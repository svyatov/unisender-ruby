# Developer experience audit

Assessed on 2026-10-26 at `2f79e96`, using Ruby 4.0.9. This report proposes changes; it does not implement or authorize releases.

The library already removes substantial integration work. Its remaining weaknesses are consistency, discoverability, and recovery from partial work. Adding every possible convenience would increase what developers must learn.

## Scope and evidence

The audit covered public operations, response types, inputs, pagination, tasks, batches, configuration, transport behavior, errors, testing support, examples, signatures, and release documentation. The source checkout and released gem were assessed separately.

The offline suite passed: `bundle exec rake test`, 467 runs, zero failures. Additional fake-transport probes checked the findings described below. No live account requests were made. No other Ruby version or full validation suite was run for this report.

Public release metadata and official UniSender documentation were checked separately. Neither deterministic tests nor documentation establish compatibility with a live account.

## Priority definitions

`P0` blocks a reliable first-use experience. `P1` fixes a concrete inconsistency or misleading behavior. `P2` removes repeated application work. `P3` needs demand or further protocol validation.

Compatibility labels describe the proposal, not a release decision. Changes to defaults, accepted input, or iteration behavior need explicit migration notes.

## First-use and correctness

### DX01. Match installation instructions to the published interface

**P0, documentation and release coordination.** RubyGems and GitHub report 0.1.1 as the latest release. The checkout declares 0.2.0 and documents its conveniences under Unreleased.

`gem install unisender-ruby` and the README quickstart therefore describe different interfaces. The Gemfile constraint `~> 0.2.0` also refers to an unpublished version. Gem metadata sends readers to the main-branch README.

Maintain separate released and development instructions. Point release metadata at versioned documentation. Validate the exact installation path and quickstart against the corresponding artifact. Publishing 0.2 is a separate authorized action.

Sources: [README](../README.md), [version](../lib/unisender/version.rb), [gemspec](../unisender.gemspec), [changelog](../CHANGELOG.md), [RubyGems latest-version metadata](https://rubygems.org/api/v1/versions/unisender-ruby/latest.json), and [0.1.1 release](https://github.com/svyatov/unisender-ruby/releases/tag/v0.1.1).

### DX02. Make the reference describe the Ruby call developers can make

**P1, documentation.** The operation index omits the implemented `records:` and `email:` alternatives. Sender requirements depend on configured defaults. Some tables list only String timestamps despite accepting Time.

Several empty-result descriptions promise no normalization, although named methods normalize legacy empty arrays. The contact-count description emphasizes the wire String without explaining the Integer reader.

Separate Ruby arguments, typed results, and raw wire shapes in each entry. Show conditional requirements and defaults where developers select the method.

Sources: [API reference](api.md), [contact operations](../lib/unisender/operations/contacts_2.rb), [result normalization](../lib/unisender/results.rb), [typed counters](../lib/unisender/records.rb), and [signatures](../sig/operations.rbs).

### DX03. Accept blocks consistently on page iterators

**P1, behavior change.** `page.each_page { ... }` returns an Enumerator without running the block. `page.auto_each` and `client.each_page` also lack block handling. Named item iterators accept blocks.

Support a block and an Enumerator consistently across these entry points. An offline probe observed zero block invocations from a fetched empty page.

Sources: [page response](../lib/unisender/page_response.rb), [helpers](../lib/unisender/helpers.rb), and [named iterators](../lib/unisender/iterators.rb).

### DX04. Use structured validation errors consistently

**P1, mostly additive diagnostics.** Invalid subscription modes raise `ValidationError` with a field and code. Missing titles, pagination limits, malformed forms, and several event failures raise plain `ArgumentError`.

Use structured errors for known operation-input failures, including the operation and a safe field path. Preserve `ArgumentError` compatibility through the existing subclass. Ruby keyword errors can retain Ruby's standard behavior.

Sources: [validation](../lib/unisender/validation.rb), [input errors](../lib/unisender/inputs.rb), [pagination validation](../lib/unisender/paginated_operations.rb), [form encoder](../lib/unisender/form.rb), and [event validation](../lib/unisender/event_payload.rb).

### DX05. Complete error categories and recovery context

**P1, additive diagnostics.** Task failures, missing messages, partial failures, closed clients, and wrapper errors can report `category: :unknown`. A generic recovery hint then provides little guidance.

Give these failures stable categories. Preserve the underlying category on batch and campaign wrappers, alongside their partial-work context. Explain the separate rescue paths for validation and service failures.

Sources: [errors](../lib/unisender/errors.rb), [diagnostics](../lib/unisender/error_diagnostics.rb), [campaign workflow](../lib/unisender/campaign_workflow.rb), and [task errors](../lib/unisender/task_response.rb). Offline probes confirmed unknown categories for task failure, missing results, and closed clients.

### DX06. Normalize known structured import cells

**P1, input behavior change.** `records:` transposes values but does not normalize them by column. An array in `email_list_ids` becomes nested form fields, although the documented cell contains comma-separated IDs.

Accept arrays for documented list and tag cells. Accept Time for documented timestamp cells. Reject unsupported structured values before sending. Preserve the explicit matrix form for wire-level control.

Do not infer that the server rejected the probed request. The offline evidence establishes a mismatch with the documented encoding.

Sources: [record rows](../lib/unisender/record_rows.rb), [form encoder](../lib/unisender/form.rb), and [official import contract](https://www.unisender.com/ru/support/api/contacts/importcontacts/).

### DX07. Prefer detailed send acceptance reports

**P1, default change requiring migration.** `send_email` omits `error_checking` by default. Upstream recommends enabling it, and the library already supports the detailed response.

Show `error_checking: true` in send examples. Evaluate making it the next minor release's default, retaining explicit legacy behavior. Do not describe acceptance as delivery.

Sources: [send operation](../lib/unisender/operations/messages_2.rb), [acceptance reports](../lib/unisender/outcomes.rb), and [official sendEmail contract](https://www.unisender.com/ru/support/api/messages/sendemail/).

### DX08. Make the typed contract reflect runtime validation

**P1, validation tightening needs compatibility review.** Signatures restrict flags to booleans or 0/1, but a probe sent `include_lists: 2`. Broad parameter aliases also accept values that specific form paths cannot serialize.

Validate known flags and closed enums locally. Narrow signatures by parameter where practical. Keep a documented low-level escape hatch for new upstream values.

Sources: [signatures](../sig/operations.rbs), [parameter type](../sig/unisender.rbs), [contact operation](../lib/unisender/operations/contacts_2.rb), and [form encoder](../lib/unisender/form.rb).

## Ruby ergonomics

### DX09. Complete familiar collection operations

**P2, additive.** Collections implement Enumerable and a small subset of Array access. `length`, slicing, and `fetch(index, default)` do not work.

Add the common operations with ordinary Ruby semantics, including `fetch` blocks. Preserve the rule that collection operations read only fetched data. Avoid promising the entire mutable Array interface.

Source: [CollectionResponse](../lib/unisender/record.rb). Offline probes confirmed these missing operations.

### DX10. Complete familiar record lookup

**P2, additive.** Records provide `[]`, one-argument `fetch`, and `dig`. They lack `key?`, `keys`, and `fetch` defaults or blocks.

Add read-only Hash conventions so callers can distinguish absent fields from explicit nulls without copying the record. Nested `dig` already works with tested String and Symbol keys.

Source: [Record](../lib/unisender/record.rb). Offline probes confirmed missing `key?` and two-argument `fetch`.

### DX11. Make conversion and serialization explicit

**P2, additive with serialization review.** Records have `to_h`; object responses do not. `JSON.generate(record)` produces an object-description String rather than its fields.

Define payload conversion consistently on object responses. Document `record.to_h.to_json` and `collection.map(&:to_h)` immediately. Evaluate explicit JSON and Rails serialization support without introducing a Rails dependency.

Keep raw envelopes available through `data`. Serialization exposes contact data and must remain an explicit caller action.

Sources: [Record and ObjectResponse](../lib/unisender/record.rb), [Response](../lib/unisender/response.rb), and the offline JSON probe.

### DX12. Finish direct readers where the contract already supplies them

**P2, additive.** `update_field` returns an ID but its generic response exposes only key lookup. Comparable creation operations provide `.id`.

Audit every documented scalar result against its readers. Start with `update_field.id`, then documented message, template, contact, and note fields. Keep dynamic fields accessible without speculative readers.

Sources: [result registry](../lib/unisender/result_registry.rb), [records](../lib/unisender/records.rb), and [official updateField contract](https://www.unisender.com/ru/support/api/inputs/updatefield/). A probe confirmed `response["id"]` works while `.id` is absent.

### DX13. Give contacts a stable address reader

**P2, additive preferred.** `Contact#email` returns a String, an EmailContact record, or nil. Callers must inspect its shape before obtaining the address.

Add a stable `email_address` reader and documented readers for requested contact details. Preserve the raw representation and existing reader during migration.

Sources: [contact records](../lib/unisender/contact_records.rb) and [contact signatures](../sig/domain_records.rbs).

### DX14. Avoid polling a task already known to be complete

**P2, observable request-count change.** Calling `.wait` on a completed task starts another status request. The handle already contains the completed result.

Return the completed handle immediately. Offer a distinct refresh operation when callers intentionally need a new observation. Define progress-callback behavior for the immediate return.

Sources: [task handle](../lib/unisender/task_response.rb) and [waiter](../lib/unisender/task_waiter.rb). The offline probe observed a second request.

### DX15. Add task-state predicates

**P2, additive.** Task users compare status strings for completion and failure. Acceptance predicates exist on other results, but task-state predicates do not.

Add `completed?`, `failed?`, and `pending?` for the documented task states. Keep task completion separate from message delivery or recipient acceptance.

Sources: [task handle](../lib/unisender/task_response.rb), [waiter states](../lib/unisender/task_waiter.rb), and [task result](../lib/unisender/records.rb).

### DX16. Provide narrow, symmetric subscription-removal inputs

**P2, additive.** Subscription creation accepts `email:`. Unsubscribe and exclude require `contact_type:` plus `contact:`.

Offer explicit email and phone convenience inputs. Make selected-list scope clear, and document all-list behavior beside the call. Keep unsubscribe and exclusion distinct because their consequences differ.

Sources: [contact operations](../lib/unisender/operations/contacts_1.rb), [subscription operations](../lib/unisender/operations/contacts_2.rb), and [official unsubscribe contract](https://www.unisender.com/ru/support/api/contacts/unsubscribe/).

### DX17. Reduce small but repeated input translations

**P2, additive with narrow scope.** Several documented choices remain arbitrary strings. `get_contact_count` also exposes the upstream nested filter object directly.

Evaluate symbols for closed choices such as template type, contact type, and note ordering. Provide explicit count-filter keywords if they remove repeated application code. Keep exact wire forms supported.

Do not accept symbols globally in the form encoder. Each mapping needs an operation-specific contract.

Sources: [input normalization](../lib/unisender/inputs.rb), [count operation](../lib/unisender/operations/contacts_1.rb), [template operations](../lib/unisender/operations/templates_1.rb), and [note operations](../lib/unisender/operations/notes_1.rb).

### DX18. Add a block-scoped client lifetime

**P2, additive.** Persistent clients require a manual `begin`/`ensure` around `close`.

Provide an explicit constructor helper such as `Client.open(...) { |client| ... }`. Close owned resources in ensure, including when the block raises. Preserve caller ownership of injected transports.

Sources: [configuration lifecycle](../lib/unisender/configuration.rb), [client construction](../lib/unisender/client_configuration.rb), and [README lifecycle example](../README.md).

## Application workflows and operations

### DX19. Expose typed import warnings

**P2, additive.** Import failures filter out `w_` entries. The raw log retains them, but callers lack a typed warning reader with row indices.

Add `row_warnings` on imports and aggregate it with global indices on batch reports. Keep envelope warnings separate. Accepted rows with warnings should remain accepted.

Sources: [import outcomes](../lib/unisender/outcomes.rb), [batch report](../lib/unisender/batch_report.rb), and [official import warning example](https://www.unisender.com/ru/support/api/contacts/importcontacts/).

### DX20. Expose page progress for checkpoints

**P2, additive.** Errors expose resume offsets, but successful pages keep their input offset and page size private.

Expose safe page metadata such as `offset`, `limit`, and `next_offset`. Show checkpointing after successful processing. Do not promise a stable snapshot or invent a total count.

Sources: [page response](../lib/unisender/page_response.rb), [pagination](../lib/unisender/pagination.rb), and [error context](../lib/unisender/errors.rb).

### DX21. Document lazy execution and consumption precisely

**P1, documentation.** Helpers return Enumerators, but returning an Enumerator does not make a subsequent `map` a lazy transformation. Reads can issue more requests when enumerated again.

Show early stopping, `.lazy.map`, and intentional materialization. Distinguish page-local iteration, all-page iteration, immediate batch commands, and lazy mutation helpers with short runnable examples.

Document replay behavior for each helper explicitly. Do not give all Enumerators one blanket replay guarantee.

Sources: [iteration](../lib/unisender/iteration.rb), [pagination](../lib/unisender/pagination.rb), [batch enumeration](../lib/unisender/batches.rb), and [README](../README.md).

### DX22. Document coordinated pacing and its limits

**P2, documentation first.** The built-in limiter is process-local. UniSender limits apply by API key or IP, including callers outside one client instance.

Explain shared egress IPs and multiple worker processes. Provide an application-owned coordination recipe. Keep external storage optional and outside runtime dependencies.

Sources: [limiter](../lib/unisender/rate_limiter.rb), [README](../README.md), and [official request limits](https://www.unisender.com/ru/support/api/common/api-limits/).

### DX23. Observe waiting as well as network attempts

**P2, additive.** Request timing starts after limiter acquisition. Retry backoff and pacing waits are absent from the emitted request duration.

Add separate safe wait and workflow measurements, with request IDs where available. Applications should distinguish slow networking from deliberate pacing or polling. Preserve the payload-free callback contract.

Sources: [request execution](../lib/unisender/request_execution.rb), [observation](../lib/unisender/observation.rb), and [retry policy](../lib/unisender/retry_policy.rb).

### DX24. Offer an explicit total budget and cancellation contract

**P3, requires transport design and tests.** Socket timeouts, retry budgets, polling deadlines, and limiter waits do not form one end-to-end deadline.

Consider a deadline that spans waits and requests, plus cancellation between batches and polls. Define what happens to in-flight mutations. Avoid promising hard interruption using only between-request checks.

Sources: [transport](../lib/unisender/transport.rb), [retry policy](../lib/unisender/retry_policy.rb), [waiter](../lib/unisender/task_waiter.rb), and [limiter](../lib/unisender/rate_limiter.rb).

### DX25. Make large-job retention a deliberate choice

**P2, opt-in behavior.** Batch enumeration retains completed responses for recovery. Immediate reports also retain every response. Streaming input alone therefore does not establish bounded memory.

Measure retention with realistic payloads. Consider summary-only retention or application checkpoint callbacks for large jobs. Preserve full reports by default until recovery guarantees have an explicit replacement.

Sources: [batch enumeration](../lib/unisender/batches.rb), [batch reports](../lib/unisender/batch_report.rb), and [record input](../lib/unisender/record_rows.rb).

### DX26. Show durable import and export recovery end to end

**P1, examples first.** The import example uses the older matrix input. The export example stops after showing the download host. Recovery advice is spread across documents.

Add complete examples using `records:`, stored task UUIDs, resume offsets, typed failures, bounded downloads, and partial-file handling. Demonstrate recovery without replaying accepted mutations.

Only add CSV or atomic-file convenience helpers after these examples identify repeated code. Validate encoding and dialect against the actual export contract.

Sources: [import example](../examples/import.rb), [export example](../examples/export.rb), [Rails guide](rails.md), [download contract](api.md#optional-workflow-helpers), and [official export documentation](https://www.unisender.com/ru/support/api/contacts/exportcontacts/).

### DX27. Cover inbound notifications when application demand warrants it

**P3, new scope.** Outbound Event Tracking exists, but named webhook management and a receiver recipe are absent. Upstream documents subscription and delivery notifications.

Start with a receiver cookbook. Then consider named hook methods and an optional decoder/verifier with bounded gzip and JSON processing. Preserve unknown fields and verify exact raw-body authentication rules.

Keep inbound notifications distinct from `track_events`. Upstream examples differ in event-key capitalization; resolve that before designing normalized records.

Sources: [public operation inventory](api.md), [event implementation](../lib/unisender/events.rb), and [official webhook documentation](https://www.unisender.com/ru/support/api/common/sistema-uvedomlenij-o-sobytiyah-webhooks/).

## Documentation, testing, and editor support

### DX28. Check documentation against public contracts

**P1, development tooling.** Ruby signatures, RBS, method tables, result readers, and examples encode overlapping facts. Existing tests do not prevent the observed documentation drift.

Add targeted agreement checks for argument names, conditional requirements, result readers, and example versions. Generate repetitive reference sections where practical, while keeping explanatory prose hand-written.

Sources: [API reference](api.md), [signatures](../sig/operations.rbs), [example tests](../test/examples_test.rb), and [consumer examples](../test/consumer/quickstart.rb).

### DX29. Improve the packaged fake transport for application tests

**P2, additive.** The fake transport checks queued operation order but lacks queue-exhaustion assertions and a JSON request reader. Its form reader targets marketing requests.

Add `verify!` or an equivalent assertion for unconsumed replies, a decoded Event Tracking payload reader, and useful sanitized mismatch diagnostics. Document request assertions for both protocols.

Sources: [testing support](../lib/unisender/testing.rb) and [testing guide](testing.md).

### DX30. Test the workflows developers actually copy

**P1, development tooling and examples.** Typed examples cover useful paths, but the main consumer example retains older access patterns. Library coverage does not prove an ergonomic consumer interface.

Check representative application code for collection access, record conversion, defaults, failures, tasks, and batch recovery. Add negative type cases for invalid combinations where the typing system supports them.

Treat the silently ignored page block as a consumer contract regression. Keep these tests focused on observable behavior.

Sources: [consumer quickstart](../test/consumer/quickstart.rb), [optional-helper consumer](../test/consumer/optional_helpers.rb), [example tests](../test/examples_test.rb), and [Steep configuration](../Steepfile).

### DX31. Provide an editor and integration path without mandatory frameworks

**P2, documentation.** RBS ships with the gem, but the consumer guide does not demonstrate editor discovery or a complete typed application setup. Rails guidance covers only a short construction example.

Document how to load the shipped signatures with the supported tooling. Show client injection, credential setup, worker ownership, and safe error reporting in a small application example.

Verify the recipe before naming an editor as supported. Keep Rails, editor plugins, and alternative type systems optional.

Sources: [signature manifest](../sig/manifest.yaml), [gemspec packaging](../unisender.gemspec), [testing guide](testing.md), and [Rails guide](rails.md).

### DX32. Validate protocol assumptions with an authorized account

**P2, separate authorization required.** The repository explicitly relies on artificial responses. That leaves real response shapes and account-specific behavior unverified.

Define an opt-in staging contract suite, with separate read-only and mutation phases. Record tested service behavior and Ruby versions. Obtain explicit permission and a designated account before running it.

This audit did not run that suite or use local credentials.

Sources: [repository verification policy](../AGENTS.md), [README limitations](../README.md), and [API contract scope](api.md).

## Design choices to defer

| Proposal | Assessment |
| --- | --- |
| A second resource-style interface, such as `client.lists.all` | Prototype only if developers struggle to discover the named methods. Two complete interfaces double documentation and support obligations. |
| Implicit pagination from ordinary `each` | Preserve page-local iteration. More network requests should remain explicit. |
| Automatic retries for sends or imports | Preserve mutation safety. A transient failure does not establish that replay is safe. |
| General `method_missing` forwarding | Prefer explicit readers for predictable typing, introspection, and errors. |
| Automatic contact-schema lookup or global configuration | Avoid hidden requests and process-wide state. Use explicit application-owned configuration. |
| A broad Rails adapter, dependency stack, or concurrent worker pool | Require a demonstrated application need and measured benefit before expanding scope. |

## Recommended sequence

1. Repair DX01 and DX02 so installation and reference material match the available interface.
2. Address DX03 through DX08 with focused public-interface tests and compatibility notes.
3. Add DX09 through DX15, DX19, and DX20 as a small, coherent response-and-task improvement.
4. Deliver DX21, DX26, and DX28 through DX31 through examples and contract checks.
5. Select remaining workflow additions from actual application needs and authorized integration evidence.

The first release should not attempt all 32 proposals. Prioritize defects and repeated caller work before adding another interface style.
